# ADR 0005: Browser session at the gateway

- **Status**: Accepted 2026-10-04

## Context

The web storefront (feature 005) is a single-page application served from the same origin as the API. Feature 004 gave
API clients bearer JWTs (15 minutes) and rotating refresh tokens (30 days), which a script-capable page would have to
store somewhere. FR-014 of the storefront spec says credentials must not be readable by page scripts, and the constitution
(Principle VII) forbids `localStorage`. The session must also end with the browser, expire after 30 minutes without
activity (clarification of 2026-10-04), keep the gateway stateless so it can scale, and leave the identity and service
contracts unchanged for API clients. The anonymous cart must survive reloads and browser restarts (US2 scenario 1).

## Decision

The gateway gains a browser-session capability, in Kotlin inside the gateway module (`services/gateway/.../browser/`);
the page never sees an access or refresh token.

- **Opt in per request.** `POST /api/v1/identity/sessions` and `/sessions/refresh` with `X-Browser-Session: cookie` are
  forwarded to identity unchanged; on 200 the gateway replaces the body by `{expiresAt, roles}` and sets the session cookie.
  Without the header nothing changes: API clients keep bearer tokens.
- **Sealed cookie.** The cookie value is an AES-256-GCM payload (access token, refresh token, `lastSeenAt`, `accountId`,
  roles) keyed by `BROWSER_SESSION_KEY` (32 bytes, Base64, generated by the bootstrap into `.env`, shared by every gateway
  replica). Attributes: `HttpOnly`, `Secure` over HTTPS, `SameSite=Strict`, `Path=/`, no `Max-Age`. Names: `__Host-session`
  and `__Host-cart` over HTTPS, `session` and `cart` over plain HTTP on localhost (the `__Host-` prefix requires `Secure`).
- **Per request.** The gateway unseals the cookie, answers 401 `unauthorized` plus a cookie deletion when `lastSeenAt` is more
  than 30 minutes old, injects `Authorization: Bearer <access>` (refreshing through identity first when under 60 s remain;
  the refresh token rotates there) and re-sets the cookie with a new `lastSeenAt`, so the idle window slides while the
  shopper is active. Sign-out forwards the revocation and deletes the cookie.
- **Cross-site protection.** `SameSite=Strict` plus, for every non-GET request that carries the cookie, `Sec-Fetch-Site`
  must be `same-origin` or `none` and `Origin`, when present, must match the host; otherwise 403 `forbidden`. A request
  carrying both the cookie and its own `Authorization` header is 400 `validation`. No CSRF token round trip.
- **Anonymous cart.** The cart contract's `X-Cart-Token` stays the API. For browsers the gateway mirrors it into a second
  sealed cookie, `__Host-cart` (`HttpOnly`, `SameSite=Lax`, 30 days), injects the header on later cart requests, removes
  the response header from browser responses and deletes the cookie after `mergeCart` succeeds.

## Consequences

- No credential is readable by page scripts, there is no `localStorage` and no token in memory: an XSS bug cannot exfiltrate
  a token (it can still act as the shopper during the session, which CSP and the lint rules aim to prevent).
- The gateway stays stateless and horizontally scalable (no Redis); the cost is one shared secret to provision and rotate.
  Rotating `BROWSER_SESSION_KEY` signs every browser out, which is acceptable for a session of 30 idle minutes.
- Identity and the other services are untouched; the browser logic is unit-, integration-, contract- and
  mutation-tested Kotlin in a module that already owns routing and security headers. The gateway takes on a second
  responsibility beyond routing, recorded in the feature's Complexity Tracking.
- The cookie carries two tokens, so it is larger than a session id and travels with every request; the 30-minute idle
  expiry is enforced by the gateway from the cookie's own timestamp, not by identity.
- A new Pact pair exists: the storefront consumes the gateway's browser-session and telemetry routes, and the gateway is
  now also a provider (`contractVerify`, [pact matrix](../../specs/005-storefront-dev-bootstrap/contracts/pact-matrix.md)).

## Alternatives considered

| Alternative | Rejected because |
|---|---|
| Identity sets the cookie itself | Spreads browser concerns into a domain service, and every replica of it, and the gateway would still have to translate cookie to bearer |
| Node backend-for-frontend (Next.js, Express, Hono) | A second backend runtime that needs its own contracts, mutation tests and security review, and duplicates what the gateway already does |
| Access token in memory plus refresh token in an HttpOnly cookie | Page scripts can still read the access token for its 15-minute life; fails FR-014 as clarified |
| Server-side sessions (Redis or database) | A new stateful component for no gain at this scale |
| Cart token in `localStorage` | Readable by scripts, against the spirit of Principle VII; a cart token inside the session cookie would not outlive the browser session |
