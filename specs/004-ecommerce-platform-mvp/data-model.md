# Data Model: E-Commerce Platform MVP

**Feature**: 004-ecommerce-platform-mvp | **Inputs**: spec.md (FR-001..FR-029), constitution Principles II (value objects, aggregates) and VI (service boundaries)

Scope: logical model only. Six services, each owning its own PostgreSQL database (FR-021); the gateway holds no data. Types below are logical (UUID, Text, Int, Long, Instant, Bool, Enum); every field that carries an invariant is a value object from section 2 and is validated at construction.

## 1. Conventions

| Topic | Rule |
|---|---|
| Identifiers | UUID, generated by the owning service. Each concept has its own typed id value object (AccountId, ProductId, OrderId, ...) so ids cannot be mixed. Cross-context references hold the id only, never a foreign key. |
| Money | `amountMinor: Long` (minor units, never negative except in adjustment/refund records where noted) + `currency: ISO-4217`. MVP is single-currency: **BRL** (decided at planning; configurable per deployment). Arithmetic only between equal currencies; overflow rejected. No tax, no shipping cost (spec Assumptions): order total = sum of line totals. |
| Time | UTC `Instant`, microsecond precision, serialised ISO-8601 with `Z`. Names end in `At`. |
| Concurrency | Each aggregate root carries a `version: Long`; writes are optimistic (compare version) so concurrent checkouts cannot oversell (FR-012). |
| Deletion | No hard deletes of business records. Catalogue uses a `withdrawn` sale state; accounts use anonymisation (FR-007); carts are deleted when emptied by order success or account deletion. |
| Anonymisation | Replace identifying fields with a pseudonym (`AccountPseudonym`, derived from AccountId, not reversible without the id) and null/clear the rest; keep ids, amounts, lines, statuses, timestamps. |
| Event envelope | JSON, AsyncAPI-described, additive changes only (Principle VI). Fields: `eventId` (UUID, unique per event), `type` (canonical name), `version` (Int, starts at 1), `occurredAt` (Instant), `aggregateId` (UUID of emitting aggregate; also partition key so one aggregate's events stay ordered), `correlationId` (CorrelationId of originating request), `payload` (object, type-specific). |
| Event publication | Each service writes the event to its own **outbox** in the same transaction as the aggregate change; a relay publishes it to Kafka (at-least-once). Consumers record `eventId` in **ProcessedEvent** and ignore duplicates (FR-022). |
| PII in events | Payloads carry the minimum needed by the consumer (Principle III). Tokens inside events (verification/reset) are single-use secrets: never logged, never stored in clear by identity (only hash). |

Tunable parameters (spec does not fix them; values decided in research.md §9–§12):

| Parameter | Decided value | FR |
|---|---|---|
| Password policy | min 12 chars, max 128, not equal to email | FR-004 |
| Sign-in throttle | throttle after 5 consecutive failures per account and per IP, for 15 min; counter reset on success | FR-006 |
| Verification token TTL | 24 h, single-use | FR-004 |
| Password reset token TTL | 1 h, single-use | FR-006 |
| Payment expiry (order `paymentStatus` still `pending`) | 30 min (spec FR-015) | FR-015 |
| Notification retry | 5 attempts, exponential backoff from 30 s capped at 10 min, then Failed | FR-019 |
| Max quantity per cart line | 99 | FR-008 |
| Simulated provider rules | rules evaluated in order, first match wins, default outcome approved: token `tok_sim_unreachable` → provider unreachable (attempt outcome `pending`; order `paymentStatus` stays `pending` and the order is cancelled with `PAYMENT_EXPIRED` after 30 min); amount minor units ending `13` → declined `insufficient_funds`; ending `14` → declined `card_expired`; token prefix `tok_sim_decline` → declined `card_rejected`; everything else (e.g. `tok_sim_approve_4242`) approved; refunds always succeed (contracts/openapi/payment.yaml) | FR-014 |

## 2. Shared value objects

Each service keeps its own copy of these definitions (shared library only if it holds no domain logic, Principle VI).

| Value object | Representation | Validation rule |
|---|---|---|
| *Id (AccountId, ProductId, CategoryId, CartId, OrderId, PaymentAttemptId, NotificationId, AddressId, ...) | UUID | Well-formed UUID; non-nil. |
| EventId | UUID | Non-nil; unique per event. |
| CorrelationId | Text | 1-64 chars of `[A-Za-z0-9-]`. Malformed or untrusted inbound value is replaced by a new one and the original kept in a separate log field (edge case, FR-025). |
| IdempotencyKey | Text | 1-128 printable ASCII, no whitespace. Required on checkout (FR-013). |
| Email | Text | Trimmed, lower-cased, max 254, single `@`, non-empty local part, domain with a dot. Compared case-insensitively. |
| Password (input only) | Text | Meets password policy; never stored, never logged. |
| PasswordHash | Text | Output of a slow adaptive hash with per-hash salt; opaque. |
| SecretToken (verification/reset/anonymous cart) | Text, 256-bit random, url-safe | Only its hash is stored; compared in constant time. |
| Role | Enum | `shopper` or `operator`; an account has a non-empty set (FR-005). |
| Money | Long + CurrencyCode | amountMinor >= 0 (see conventions); currency is a known ISO-4217 code equal to platform currency. |
| Quantity | Int | 1..99 per line (decided at planning). Zero is not a Quantity; "set to 0" is expressed as line removal (US2). |
| StockLevel | Int | >= 0. Adjustment delta is a signed Int, non-zero. |
| Sku | Text | 3-32 chars `[A-Z0-9-]`, unique within catalogue. |
| ProductName / CategoryName | Text | Trimmed, 1-120 chars, no control characters. |
| Description | Text | 0-4000 chars, sanitised for display. |
| ImageRef | Text (URL or storage key) | Max 2048 chars, https or storage key; at most 10 per product; exactly one primary. |
| PostalAddress | Record | recipientName 1-100; line1 1-120; line2 0-120; city 1-80; region 0-80; postalCode 1-20; countryCode ISO-3166 alpha-2. |
| PhoneNumber | Text | E.164 (`+` and 8-15 digits). |
| OrderNumber | Text | Human-readable, unique, immutable; derived at placement (spec mentions "order number" in notifications, format unspecified). |
| OrderStatus | Enum | `placed`, `preparing`, `shipped`, `delivered`, `cancelled` (FR-015). Payment is not part of this lifecycle. |
| PaymentStatus | Enum | `pending`, `approved`, `failed` (FR-015). Independent of OrderStatus; see section 3.4. |
| CancellationReason | Enum | `SHOPPER_REQUEST`, `OPERATOR`, `PAYMENT_FAILED`, `PAYMENT_EXPIRED` (FR-015). Mandatory on every cancellation. |
| CartRevision | Text (opaque) | 1-128 printable ASCII; compared for equality only, never parsed by clients (FR-010). |
| PaymentMethodRef | Text | Opaque simulated-provider token; never card numbers (Principle III). |
| ProviderReference | Text | 1-64 chars, assigned by provider (simulated). |
| PaymentOutcome | Enum | Outcome of one payment attempt: `approved`, `declined`, `pending` (see section 3.5). Not an order status; maps to PaymentStatus in section 3.5. |
| DeclineCategory | Enum | Coarse categories only (e.g. `insufficient_funds`, `method_rejected`, `suspected_fraud`); shown to shopper (US4.2). |
| NotificationChannel | Enum | `email`, `sms`. |
| NotificationKind | Enum | `account_verification`, `password_reset`, `order_confirmation`, `payment_failure`, `order_shipped`, `order_delivered`. |
| DeliveryStatus | Enum | `queued`, `sent`, `failed`, `suppressed`. |
| StockAdjustmentReason | Text | 3-200 chars, mandatory (FR-002). |
| PageRequest | Record | page >= 0, size 1..100, whitelisted sort keys. |

## 3. Bounded contexts

### 3.1 Identity (service: identity; FR-004..FR-007)

**Aggregates / entities**

| Entity | Fields | Constraints |
|---|---|---|
| Account (root) | id: AccountId; email: Email; passwordHash: PasswordHash; status: AccountStatus; roles: Set<Role>; verifiedAt: Instant?; failedSignInCount: Int; lockedUntil: Instant?; createdAt; deletedAt: Instant?; pseudonym: AccountPseudonym?; version | email unique among non-deleted accounts; roles non-empty; status drives allowed actions. |
| Profile (inside Account) | displayName: Text?; locale fixed for MVP | Data minimised (FR-007): no birth date, no gender. |
| Address (entity of Account) | id: AddressId; label: Text; address: PostalAddress; phone: PhoneNumber?; isDefault: Bool | At most one default; max 10 per account; removing the default promotes none. |
| VerificationToken | accountId; tokenHash; expiresAt; usedAt? | Single use; only latest valid per account. |
| PasswordResetToken | accountId; tokenHash; expiresAt; usedAt? | Single use; issuing a new one invalidates older ones (FR-006). |
| SessionRecord | id; accountId; issuedAt; expiresAt; revokedAt? | Revoked on sign-out, password change, deletion. |
| OutboxMessage / ProcessedEvent | see conventions | |

**Invariants**

| Rule | FR |
|---|---|
| Registration creates an `unverified` account; duplicate email refused with a generic message that does not reveal existence to unauthenticated callers. | FR-004 |
| Sign-in only when `verified` and not locked; wrong credentials and unknown email produce the same response; 5th consecutive failure sets `lockedUntil`. | FR-004, FR-006 |
| Reset: token valid only if unused and unexpired; setting a new password marks token used, revokes all sessions, resets the failure counter; the old password stops working. | FR-006 |
| Operator role cannot be self-assigned; roles are granted only by seed or an operator. | FR-005 |
| Address edits only by the owning account. | FR-004, FR-005 |
| Deletion anonymises: email replaced by an unusable placeholder, hash cleared, profile and all addresses removed, sessions revoked, status `deleted`; AccountId and pseudonym kept. | FR-007 |
| Email is immutable in MVP (no change-email journey in spec). | FR-007 |

**Account state machine (verification and deletion)**

| From | Event/command | To | Guard |
|---|---|---|---|
| (none) | Register | unverified | policy met, email unused |
| unverified | VerifyEmail(token) | verified | token valid, unused, unexpired |
| unverified, verified | DeleteAccount | deleted | caller is owner; terminal |
| deleted | any | refused | terminal |

Lock state (`lockedUntil`) is orthogonal to status and expires by time.

**Events published**: AccountRegistered (payload: accountId, email, verification token), AccountVerified, AccountDeleted (accountId, pseudonym), PasswordResetRequested (accountId, email, reset token).
**Events consumed**: none.
**Read-model copies**: none. Identity is the source of truth for email, roles and addresses; other contexts receive snapshots (below).

### 3.2 Catalog (service: catalog; FR-001..FR-003, FR-012)

**Aggregates / entities**

| Entity | Fields | Constraints |
|---|---|---|
| Category (root) | id; name: CategoryName; parentId: CategoryId?; status: `active`/`withdrawn` | name unique per parent; no cycles; max depth 4. |
| Product (root) | id; sku: Sku; name; description; images: List<ImageRef>; price: Money; categoryId; saleState: `active`/`withdrawn`; createdAt; updatedAt; version | sku unique; price > 0; category must be active; withdrawing is reversible by operator, never deleted. |
| InventoryLevel (root, one per product) | productId; onHand: StockLevel; reserved: StockLevel; version | `reserved <= onHand`; `available = onHand - reserved >= 0` always. |
| StockReservation (root, keyed by orderId) | orderId; lines: List<(productId, Quantity)>; status: `reserved`/`committed`/`released`; createdAt; resolvedAt? | One per order (natural idempotency); lines at least one. |
| StockAdjustment (append-only) | id; productId; delta: Int; reason; operatorId: AccountId; at; resulting onHand | Reason mandatory; result may not make onHand < reserved. |
| AuditEntry (append-only) | id; operatorId; action; targetId; at; correlationId | Written for every catalogue change and every refused operator attempt (US7.4). |
| OutboxMessage / ProcessedEvent | see conventions | |

**Invariants**

| Rule | FR |
|---|---|
| Browse/search return only `active` products in `active` categories; withdrawn never appear; zero available is shown as out of stock. | FR-001, FR-003 |
| Only operators mutate catalogue; shopper attempts refused and audited. | FR-002, FR-005 |
| Reserve is all-or-nothing across order lines in one local unit of work: if any line has `available < qty`, nothing is reserved and the caller learns which product is short. | FR-012, US4.3, US4.5 |
| Reserve of an already-reserved orderId is a no-op returning the existing reservation. | FR-013 |
| Commit: `onHand -= qty`, `reserved -= qty`. Release: `reserved -= qty`. Restock after cancel of an order whose reservation was already committed (paymentStatus `approved`): `onHand += qty`. Each transition legal once from the right state. | FR-012, FR-016 |
| Concurrent reserves of the last unit: exactly one succeeds (conditional update on version); stock never negative. | SC-004 |
| Adjustment is signed, attributed, time-stamped, with reason. | FR-002 |

**Reservation state machine**

| From | Trigger | To |
|---|---|---|
| (none) | reserve request (synchronous query/command from order, at checkout and before any payment attempt, FR-012) | reserved (publishes StockReserved) |
| reserved | OrderPaid | committed (StockCommitted) |
| reserved | OrderPaymentFailed, OrderCancelled (any reason, including `PAYMENT_EXPIRED`) | released (StockReservationReleased) |
| committed | OrderCancelled | released with restock (StockReservationReleased, flag restocked) |
| committed, released | any other | refused / ignored |

**Events published**: StockReserved, StockReservationReleased, StockCommitted.
**Events consumed**: OrderPaid, OrderPaymentFailed, OrderCancelled.
**Read-model copies**: none. (Reserve is a synchronous API call from order, one hop; rejection is the call's error response, there is no canonical rejection event.)

### 3.3 Cart (service: cart; FR-008..FR-010)

**Aggregates / entities**

| Entity | Fields | Constraints |
|---|---|---|
| Cart (root) | id: CartId; owner: `Account(AccountId)` or `Anonymous(SecretToken hash)`; lines: List<CartLine>; revision: CartRevision; updatedAt; version | One active cart per account; anonymous cart is addressed by an opaque token; at most 100 lines; one line per productId. |
| CartLine | productId; sku: Sku; nameSnapshot: ProductName; quantity: Quantity; priceAtAdd: Money; addedAt | quantity <= available at add time and <= max per line. |
| OutboxMessage / ProcessedEvent | see conventions | |

**Invariants**

| Rule | FR |
|---|---|
| Add/update/remove allowed to anonymous and signed-in callers; total = sum(quantity x priceAtAdd) shown with current prices (see below). | FR-008 |
| Quantity capped at available stock; refusal states available quantity; set to 0 removes the line. | FR-008, US2.2, US2.5 |
| Withdrawn or zero-stock products cannot be added. | FR-003 |
| Viewing a cart fetches current price and availability from catalog (query API); a line whose current price differs from priceAtAdd is flagged with both prices; `priceAtAdd` is refreshed only when the shopper acknowledges (by checking out with the new revision, see section 3.4) or on next add. | FR-010 |
| `revision` is an opaque string returned with every cart view and mutation. It MUST change whenever any line, any quantity or any line's current price changes, and MUST stay the same otherwise. Because prices are read live from catalog, it is derived (digest of cart version plus each line's productId, quantity and current unit price) and recomputed on each view; clients treat it as opaque and send back the last one they saw at checkout. | FR-010, FR-011 |
| Merge on sign-in: for each product, `min(sum of quantities, available)`; result lists any capped lines; source anonymous cart is deleted. Two anonymous carts merge sequentially with the same rule. | FR-009 |
| Cart is emptied only after order success (payment approved), never on payment failure, refused checkout or cancellation. | US4 |

**State machine**: none (cart exists or not). Anonymous to account is a merge operation, not a state.

**Events published**: CartMerged (accountId, merged line count, capped product ids).
**Events consumed**: OrderPaid (payment approved: clear that account's cart lines for the ordered cart), AccountDeleted (delete account cart).
**Read-model copies**: per line `sku`, `nameSnapshot`, `priceAtAdd`. Current price/availability are read live from catalog, not copied.

### 3.4 Order (service: order; FR-011..FR-017)

**Aggregates / entities**

| Entity | Fields | Constraints |
|---|---|---|
| Order (root) | id: OrderId; number: OrderNumber; accountId: AccountId; orderStatus: OrderStatus; paymentStatus: PaymentStatus; lines: List<OrderLine>; total: Money; deliveryAddress: PostalAddress (snapshot) + contact phone?; paymentMethodRef; placedAt; paymentExpiresAt: Instant? (placedAt + 30 min while paymentStatus is `pending`, else null); cancellation: (reason: CancellationReason, at, by)?; refundRecordedAt?; history: List<StatusChange>; version | At least one line; total = sum(lineTotal), > 0; lines, prices, total, address immutable after placement and frozen at the current catalogue prices at confirmation (FR-011); `cancellation` present if and only if orderStatus is `cancelled`; paymentStatus is `approved` whenever orderStatus is `preparing`, `shipped` or `delivered` (FR-015). |
| OrderLine | productId; sku; nameSnapshot; unitPrice: Money; quantity: Quantity; lineTotal: Money | lineTotal = unitPrice x quantity; frozen. |
| StatusChange | statusKind: `order`/`payment`; from; to; at; actorType: `shopper`/`operator`/`system`; actorId?; reason: CancellationReason? | Append-only; one per transition of either status; reason set when `to` = `cancelled`. |
| IdempotencyRecord | key: IdempotencyKey; accountId; requestHash; orderId; responseSnapshot; createdAt; expiresAt (+24 h) | Unique per (accountId, key). |
| OutboxMessage / ProcessedEvent | see conventions | |

**Invariants**

| Rule | FR |
|---|---|
| Placement requires an authenticated shopper, non-empty cart contents, a delivery address that belongs to the caller, the cart revision the shopper last saw, and a successful stock reservation; otherwise no order is created. | FR-005, FR-011, US4.5 |
| Stale cart revision: the checkout request carries `cartRevision`. If it differs from the cart's current revision because any line's price changed, checkout is refused listing each changed line with old and new prices; no order and no reservation is created. The shopper confirms by resubmitting with the new revision. The check runs before stock reservation, so nothing needs releasing. | FR-010, FR-011 |
| Stock is reserved by a synchronous request to catalog before any payment attempt; if any line is unavailable the checkout is refused naming those lines and no order is created. | FR-012 |
| Same (account, key) with same request hash returns the original outcome (one order, one payment attempt); same key with a different hash is refused as a conflict; record expires after 24 h. Refusals that create no order (stale cart revision, insufficient stock) store no IdempotencyRecord, so the shopper can resubmit with the new revision under the same key. | FR-013 |
| Orders carry two independent statuses, `orderStatus` and `paymentStatus`; only legal transitions in the tables below, others refused, order unchanged, no history entry. | FR-015, US5.5 |
| Guard: an order moves to `preparing` only while `paymentStatus` = `approved`; with `pending` or `failed` the transition is refused. | FR-015 |
| Shoppers read only their own orders; operators read all. | FR-016 |
| Cancellation reasons: `SHOPPER_REQUEST`, `OPERATOR`, `PAYMENT_FAILED`, `PAYMENT_EXPIRED`; one is recorded on every cancellation. Shoppers cancel only while orderStatus is `placed`; operators cancel while `placed` or `preparing`; `shipped` and `delivered` are not cancellable. Operators advance status. | FR-015, FR-016, FR-017 |
| On cancel of an order whose paymentStatus is `approved` a refund is requested (OrderCancelled consumed by payment), stock is restocked, and `refundRecordedAt` is set when RefundRecorded arrives. On cancel with paymentStatus `pending` the reservation is released and the pending attempt voided. | FR-012, FR-016 |
| Payment failure: PaymentDeclined sets paymentStatus `failed` and, in the same transaction, cancels the order with reason `PAYMENT_FAILED` and publishes OrderPaymentFailed; catalog releases the reservation. | FR-012, FR-015 |
| Expiry: an order still `placed` with paymentStatus `pending` after `paymentExpiresAt` (30 min) is cancelled by a scheduled job with reason `PAYMENT_EXPIRED` (paymentStatus set to `failed`, pending attempt voided), publishing OrderCancelled and releasing stock. A late PaymentApproved for an already cancelled order is refunded by payment (section 3.5). | FR-012, FR-015 |
| Account deletion: order keeps ids, lines, totals, statuses under pseudonym; delivery address snapshot is scrubbed once the order reaches a terminal orderStatus, `delivered` or `cancelled` (immediately if already there). | FR-007 |

**Order status (`orderStatus`) state machine**

| From | To | Trigger | Actor | Guard | Event published |
|---|---|---|---|---|---|
| (none) | placed | Checkout accepted (cart revision current, stock reserved); paymentStatus starts at `pending` and the 30-min expiry clock starts in the same transaction | shopper | none | OrderPlaced |
| placed | preparing | Operator action | operator | paymentStatus = `approved` | OrderPreparing |
| preparing | shipped | Operator action | operator | none | OrderShipped |
| shipped | delivered | Operator action | operator | none | OrderDelivered |
| placed | cancelled | Shopper cancel (`SHOPPER_REQUEST`), operator cancel (`OPERATOR`), payment failure (`PAYMENT_FAILED`) or payment expiry (`PAYMENT_EXPIRED`) | shopper/operator/system | none | OrderCancelled (OrderPaymentFailed instead for `PAYMENT_FAILED`) |
| preparing | cancelled | Operator cancel (`OPERATOR`) only | operator | none | OrderCancelled |
| shipped, delivered, cancelled | any | none (terminal) | | | refused |
| any other pair (e.g. placed->shipped, preparing->placed, shipped->cancelled) | | | | | refused |

**Payment status (`paymentStatus`) state machine**

| From | To | Trigger | Actor | Event published |
|---|---|---|---|---|
| (none) | pending | Placement, same transaction; starts the 30-min expiry clock | system | (none extra) |
| pending | approved | PaymentApproved; order stays `placed` | system | OrderPaid |
| pending | failed | PaymentDeclined; order is cancelled with `PAYMENT_FAILED` in the same transaction | system | OrderPaymentFailed |
| pending | failed | Expiry: still pending after 30 min; order is cancelled with `PAYMENT_EXPIRED` in the same transaction | system | OrderCancelled |
| approved, failed | any | none (terminal; cancellation of an approved order leaves paymentStatus `approved` and records a refund) | | refused |

PaymentPending is consumed only to annotate the order (provider unreachable, shopper may retry); paymentStatus stays `pending`.

**Events published**: OrderPlaced, OrderPaid, OrderPaymentFailed, OrderPreparing, OrderShipped, OrderDelivered, OrderCancelled.
**Events consumed**: PaymentApproved, PaymentDeclined, PaymentPending, RefundRecorded, AccountDeleted.
**Read-model copies**: per line `sku`, `nameSnapshot`, `unitPrice`, `quantity`; delivery address snapshot (copied from identity at checkout request time); `orderNumber`. Order payloads carry what notification and payment need (accountId, total, lines, address, payment method ref) so no callback is required.

### 3.5 Payment (service: payment; FR-013, FR-014, FR-016)

**Aggregates / entities**

| Entity | Fields | Constraints |
|---|---|---|
| PaymentAttempt (root) | id: PaymentAttemptId; orderId: OrderId; kind: `charge`/`refund`; amount: Money; paymentMethodRef; attemptNumber: Int; idempotencyKey (derived: orderId + kind + attemptNumber); outcome: PaymentOutcome; providerReference: ProviderReference?; declineCategory: DeclineCategory?; createdAt; resolvedAt?; version | Unique (orderId, kind, attemptNumber); amount > 0; at most one `approved` charge per order; refund amount <= approved charge amount; declineCategory only when declined. |
| RefundRecord | attemptId (kind `refund`); chargeAttemptId; recordedAt | One refund per order cancellation (MVP: full refund only). |
| OutboxMessage / ProcessedEvent | see conventions | |

**Invariants**

| Rule | FR |
|---|---|
| Provider is behind a port; MVP adapter is the simulator whose deterministic rules map amount/method to `approved`, `declined(category)` or `pending` (provider unreachable). Order journey is identical for any adapter. | FR-014 |
| One OrderPlaced produces exactly one charge attempt; duplicate event or retry never creates a second approved charge. | FR-013 |
| Pending attempts are re-attempted (scheduled, bounded) until resolved or the order is cancelled; a retry reuses the order, adds attemptNumber + 1 only after the previous one is resolved or voided. | US4.6 |
| OrderCancelled for an order with an approved charge records a refund (full amount) and publishes RefundRecorded; with only a pending charge, the attempt is voided (an approval racing in after cancel is refunded automatically). | FR-016 |
| No card data stored; only PaymentMethodRef. | Principle III |

**Mapping to the order's paymentStatus** (the payment context owns attempts; the order context owns paymentStatus and updates it only from these events)

| Attempt outcome / event | Order paymentStatus |
|---|---|
| none yet, or `pending` (PaymentPending) | `pending` |
| `approved` (PaymentApproved) | `approved` |
| `declined` (PaymentDeclined) | `failed`, order cancelled `PAYMENT_FAILED` |
| `voided` after expiry (order-side expiry, no payment event) | `failed`, order cancelled `PAYMENT_EXPIRED` |

**PaymentAttempt outcome state machine**

| From | Trigger | To | Event published |
|---|---|---|---|
| (none) | OrderPlaced, provider approves | approved | PaymentApproved |
| (none) | OrderPlaced, provider declines | declined | PaymentDeclined (with DeclineCategory) |
| (none) | OrderPlaced, provider unreachable | pending | PaymentPending |
| pending | scheduled/shopper retry approved | approved | PaymentApproved |
| pending | retry declined | declined | PaymentDeclined |
| pending | OrderCancelled (incl. expiry) | voided | (none) |
| (none, kind refund) | OrderCancelled with approved charge | approved (recorded) | RefundRecorded |
| approved, declined, voided | any | refused (terminal) | |

**Events published**: PaymentApproved, PaymentDeclined, PaymentPending, RefundRecorded.
**Events consumed**: OrderPlaced, OrderCancelled.
**Read-model copies**: from OrderPlaced: orderId, accountId, total, paymentMethodRef (stored on the attempt). No catalogue or identity data.

### 3.6 Notification (service: notification; FR-018..FR-020)

**Aggregates / entities**

| Entity | Fields | Constraints |
|---|---|---|
| Recipient (root; read model keyed by accountId) | accountId; emailSnapshot: Email; emailVerified: Bool; status: `active`/`anonymised`; preferences: NotificationPreference | Built from AccountRegistered/AccountVerified; anonymised on AccountDeleted (email cleared). |
| NotificationPreference (inside Recipient) | emailEnabled (default true); smsOptIn (default false); phone: PhoneNumber?; phoneVerifiedAt: Instant? | SMS used only if smsOptIn and phoneVerifiedAt set. Email cannot be switched off for security kinds (`account_verification`, `password_reset`). |
| Notification (root) | id: NotificationId; sourceEventId: EventId; kind; channel; recipientAccountId; recipientAddress (email or phone, snapshot); content: rendered subject/body snapshot; status: DeliveryStatus; attempts: Int; nextAttemptAt?; lastFailure?; createdAt; sentAt? | Unique (sourceEventId, kind, channel) = dedupe by event id (FR-019). Content contains no secrets beyond what the message must carry. |
| DeliveryAttempt | notificationId; at; result; failureCategory? | Append-only. |
| OutboxMessage / ProcessedEvent | see conventions | |

**Invariants**

| Rule | FR |
|---|---|
| One consumed event yields at most one Notification per channel; duplicates ignored. | FR-019, SC-005 |
| Channels selected at creation from current preferences: email always (default); plus SMS when opted in with verified number (e.g. OrderShipped yields both). | FR-018, US6.2 |
| Preferences are read when the next event is processed, so changes apply immediately. | FR-020, US6.5 |
| Content per kind: order confirmation has order number, lines, total, delivery address; payment failure has decline category. | US6.1 |
| Retries with exponential backoff up to max attempts, then `failed`; failures listed for operators; order flow never depends on delivery. | FR-019 |
| Anonymised or deleted recipients receive nothing; their queued notifications become `suppressed`. | FR-007 |
| Operator-only access to failed-delivery list; shopper can read/write only own preferences. | FR-005, FR-020 |

**Delivery status state machine**

| From | Trigger | To | Event published |
|---|---|---|---|
| (none) | event consumed, channel selected | queued | (none) |
| queued | attempt succeeds | sent | NotificationSent |
| queued | attempt fails, attempts < max | queued (nextAttemptAt = backoff) | (none) |
| queued | attempt fails, attempts = max | failed | NotificationFailed |
| queued | recipient anonymised / channel no longer permitted | suppressed | (none) |
| sent, failed, suppressed | any | refused (terminal) | |

Phone verification (code challenge) lives here; mechanism not specified in spec.

**Events published**: NotificationSent, NotificationFailed.
**Events consumed**: AccountRegistered, AccountVerified, AccountDeleted, PasswordResetRequested, OrderPaid, OrderPaymentFailed, OrderShipped, OrderDelivered.
**Read-model copies**: recipient email snapshot (from AccountRegistered), verification flag (from AccountVerified), order content snapshot inside each Notification (from order event payloads).

## 4. Cross-context relationships

Reference by id only; no cross-database joins or shared tables (FR-021).

| Holder | References | Via | Purpose |
|---|---|---|---|
| cart | AccountId (identity); ProductId (catalog) | token claim; stored | ownership; line product |
| order | AccountId; ProductId; AddressId (not stored, address copied) | token claim; stored | owner; line snapshot |
| payment | OrderId; AccountId | stored from OrderPlaced | charge subject |
| catalog | OrderId (reservation); operator AccountId | stored | reservation key; audit |
| notification | AccountId; OrderId (inside content/source event) | stored from events | recipient; message context |
| identity | none | | root of identity; others point at it |

Synchronous calls (one hop each, Principle VI): cart -> catalog (price, availability); order -> catalog (reserve, all-or-nothing); order -> identity (address by id for the caller, at checkout). Everything else is event-driven.

Event meanings after the order/payment status split: **OrderPaid** = payment approved; the order remains `placed` with paymentStatus `approved` and becomes eligible for `preparing`. **OrderPaymentFailed** = payment failed and the order is cancelled with reason `PAYMENT_FAILED` (it replaces OrderCancelled for that case, so consumers see one release signal). **OrderCancelled** covers `SHOPPER_REQUEST`, `OPERATOR` and `PAYMENT_EXPIRED`. Payment attempt outcomes `approved`, `declined` and `pending` stay internal to the payment context and its PaymentApproved, PaymentDeclined and PaymentPending events.

Checkout flow, for task derivation: Order checks the submitted cart revision (stale: refuse, listing changed lines with old and new prices, nothing created) -> reserves stock (sync, before payment; shortage: refuse, naming unavailable lines) -> persists order with orderStatus `placed` and paymentStatus `pending` -> OrderPlaced -> Payment charges -> PaymentApproved -> paymentStatus `approved` + OrderPaid (order stays `placed`) -> catalog commits (StockCommitted), cart clears, notification sends; operator may then move the order to `preparing`. Decline: PaymentDeclined -> paymentStatus `failed`, order `cancelled` (`PAYMENT_FAILED`) + OrderPaymentFailed -> catalog releases, cart kept, notification sends. Expiry: paymentStatus still `pending` after 30 min -> paymentStatus `failed`, order `cancelled` (`PAYMENT_EXPIRED`) + OrderCancelled -> catalog releases, payment voids the pending attempt.

## 5. Data retention

| Data | Owner | Retention / expiry | Mechanism |
|---|---|---|---|
| IdempotencyRecord | order | 24 h from creation; replay within window returns stored outcome | scheduled purge by `expiresAt` |
| ProcessedEvent (eventId, consumer) | every consuming service | 7 days (longer than max broker redelivery window) | scheduled purge |
| OutboxMessage | every publishing service | Delete 7 days after published | scheduled purge |
| VerificationToken | identity | 24 h or on use; hash only; purged 7 days after expiry | purge |
| PasswordResetToken | identity | 1 h or on use; hash only; purged 7 days after expiry | purge |
| SessionRecord | identity | until expiry/revoke; purged 30 days later | purge |
| Anonymous cart | cart | 30 days idle (decided at planning) | scheduled purge |
| Account PII (email, hash, profile, addresses) | identity | until deletion request, then anonymised immediately (FR-007) | AccountDeleted |
| Order financial record | order, payment | Kept indefinitely (financial record); PII scrubbed per 3.4 | AccountDeleted handler |
| Notification content | notification | 90 days (decided at planning); recipient address cleared on anonymisation | purge, AccountDeleted |
| StockAdjustment, AuditEntry | catalog | Kept (attribution/audit, FR-002); operator id is pseudonymous | none |
| Logs | platform | No PII or secrets in any log (Principle III); correlation id only | n/a |
