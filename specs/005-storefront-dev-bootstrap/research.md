# Research: Web Storefront and Local Development Bootstrap

**Feature**: 005 | **Date**: 2026-10-04 | **Spec**: [spec.md](spec.md)

Every decision below resolves an unknown of the plan's Technical Context or records how an existing
platform fact (feature 004) shapes this feature. Format: Decision / Rationale / Alternatives.

## 1. Storefront runtime shape: static single-page application behind the gateway

**Decision**: The storefront is a Vite-built static bundle served by a small unprivileged static
file container (`storefront`, `nginxinc/nginx-unprivileged` pinned by digest, listening on 8080,
SPA fallback to `index.html`, long-cache hashed assets, no-cache `index.html`). It joins the `core`
profile on the `internal` network only. The gateway gets one new catch-all route, evaluated after
every `/api/**` route: `GET`/`HEAD` on anything that is not `/api/**`, `/actuator/**` or
`/.well-known/**` → `storefront`. Non-GET requests to unknown paths keep answering 404 `not-found`.

**Rationale**: FR-013 requires one origin and one entry point; a static container is the cheapest
way to serve the bundle inside the existing Compose stack and does not add a second application
runtime. The gateway already owns security headers, correlation ids, rate limits and access logs
for everything the browser touches.

**Alternatives**: serving the bundle from the gateway's own classpath (couples the Kotlin build to
npm and makes the gateway image depend on Node); a Node server (Next.js or a custom Express/Hono
server) as the storefront container (adds a server runtime that would itself need contracts,
mutation tests and security review, see §2); a separate published port with CORS (violates FR-013
and complicates cookies).

## 2. Browser authentication: gateway-managed encrypted session cookie, tokens never reach the page

**Decision**: The gateway gains a *browser session* capability, implemented in Kotlin inside the
gateway module (`services/gateway/.../browser/`), so that the page never sees an access or refresh
token:

- Sign-in, refresh and sign-out keep their identity contracts unchanged. When a request to
  `POST /api/v1/identity/sessions` or `/sessions/refresh` carries the header
  `X-Browser-Session: cookie`, the gateway forwards it, and on 200 replaces the JSON body by
  `{ "expiresAt": ..., "roles": [...] }` and sets the cookie `__Host-session` (HttpOnly, Secure
  when the request was HTTPS, `SameSite=Strict`, `Path=/`, no `Max-Age`: a browser-session cookie).
- The cookie value is an AES-256-GCM sealed payload keyed by `BROWSER_SESSION_KEY` (32 bytes,
  Base64, generated by the bootstrap into `.env` like `IDENTITY_SIGNING_KEY`; every gateway replica
  shares it, so the gateway stays stateless and scalable). Payload: access token, refresh token,
  `lastSeenAt`, `accountId`, roles.
- On any request carrying `__Host-session`, the gateway unseals it, rejects it when `lastSeenAt` is
  older than 30 minutes (answer 401 `unauthorized` plus a cookie deletion), otherwise injects
  `Authorization: Bearer <access>`; when the access token has less than 60 s left it refreshes
  through identity first (the refresh token rotates there). Every response that used the cookie
  re-sets it with a new `lastSeenAt` (silent renewal while active, FR-014).
- `DELETE /api/v1/identity/sessions/current` with the cookie forwards the revocation and deletes
  the cookie.
- Cross-site protection: `SameSite=Strict` plus, for every non-GET request that carries the cookie,
  the gateway requires `Sec-Fetch-Site` to be `same-origin` (or `none`) and `Origin` (when present)
  to match the request host; otherwise 403 `forbidden`. No CSRF token round-trip is needed.
- A request that carries both the cookie and its own `Authorization` header is answered 400
  `validation`; API clients keep using bearer tokens exactly as before.
- Cookie names follow the scheme: `__Host-session` and `__Host-cart` (with `Secure`) when the
  request arrived over HTTPS, `session` and `cart` with the same attributes minus `Secure` over
  plain HTTP (local development on `http://localhost`), because the `__Host-` prefix is only
  valid with `Secure`. The gateway accepts whichever name is present, never both.

**Rationale**: FR-014 ("credentials MUST NOT be readable by page scripts") rules out the usual
in-memory access token, and constitution VII forbids `localStorage`. An encrypted cookie keeps the
gateway stateless (no Redis), reuses identity's rotating refresh tokens and the existing JWT
validation, and puts the logic where it is unit-, integration-, contract- and mutation-tested Kotlin.
Idle expiry of 30 minutes and "ends with the browser" come straight from the clarification.

**Alternatives**: identity setting the cookie itself (spreads browser concerns into a domain
service and every replica would need the same change); a Node backend-for-frontend (second runtime,
duplicates the gateway); access token in memory + refresh token in an HttpOnly cookie (page scripts
can still exfiltrate the access token during its 15-minute life; fails FR-014 as clarified);
server-side sessions in Redis (new stateful component for no gain at this scale).

## 3. Anonymous cart persistence: cart token in a persistent HttpOnly cookie

**Decision**: The cart contract's `X-Cart-Token` stays the platform API. For browsers the gateway
mirrors it: when a cart response carries `X-Cart-Token` and the request carried
`X-Browser-Session: cookie`, the gateway also sets `__Host-cart` (HttpOnly, `SameSite=Lax`,
`Max-Age` 30 days, sealed with the same key) and, on later cart requests without an explicit
`X-Cart-Token`, injects the header from the cookie. After `mergeCart` succeeds the gateway deletes
`__Host-cart`. The response header is removed from browser responses.

**Rationale**: The spec requires the cart to survive reloads and browser restarts (US2 scenario 1);
the cart token is a capability credential and should not live in `localStorage` or be readable by
scripts. `SameSite=Lax` is enough for a cart (no cross-site state change risk beyond adding lines,
and non-GET requests still pass the §2 origin check).

**Alternatives**: `localStorage` cart token (readable by scripts; against the spirit of
constitution VII); cart token inside `__Host-session` (an anonymous cart has no session and must
outlive the browser session).

## 4. Browser telemetry: OpenTelemetry Web SDK through a gateway route to the collector

**Decision**: The storefront uses the OpenTelemetry JavaScript web SDK (`@opentelemetry/sdk-trace-web`
with the document-load, fetch and user-interaction instrumentations, plus the logs SDK for client
errors) exporting OTLP/HTTP JSON to `POST /api/v1/telemetry/v1/traces` and `/api/v1/telemetry/v1/logs`.
The gateway routes both to the collector's existing OTLP/HTTP receiver (`otel-collector:4318`,
rewriting the prefix), anonymous, tier `browse` rate limit charged per source address, body limit
256 KiB, `POST` only, cookies and `Authorization` stripped before forwarding; when the
`observability` profile is down the route answers 503 and the storefront drops the batch (FR-032).
Resource attributes: `service.name=storefront`, `service.version`, a random
`session.id` (UUID kept in `sessionStorage`, never a credential) and `correlation.id`. Fetch
instrumentation propagates `traceparent` and the storefront sets `X-Correlation-Id` (a UUID per
page view, renewed per user action) on every request, so browser spans, the gateway access line and
every service line join on both ids (SC-011).

**Privacy by construction (FR-032)**: a storefront `telemetry` module owns the only exporter and
applies an allow-list of attributes; URL attributes are replaced by the route template
(`/products/:id`), query strings are dropped, no form values, no search terms, no free text, no
account id. The collector adds a second layer: an `attributes` processor deleting `http.url`,
`http.target`, `url.full`, `url.query`, `user.*`, `enduser.*` and a `redaction` processor on the
`storefront` service. Navigation paths and interaction events (option D) are therefore recorded as
route templates and element roles/ids, never as typed content.

**Rationale**: reuses the collector, Tempo, Loki and Grafana already provisioned; OTLP from the
browser is the standard shape and needs no new service; the gateway route is the single entry point
and provides throttling for free.

**Alternatives**: a bespoke `/events` endpoint in a service (new backend code and schema to
maintain; loses trace joins); Grafana Faro SDK (needs the Faro receiver on the collector and a second
protocol; revisit if session replay is ever wanted); exposing the collector port to the host
(violates FR-013 and the "nothing but the gateway is published" rule).

## 5. Frontend toolchain and libraries

**Decision** (constitution VII and Technology Stack):

| Concern | Choice |
|---------|--------|
| Runtime | Node 24 LTS (`frontend/.nvmrc`, `engines` in `package.json`, enforced by `npm` `engine-strict`); npm with a committed `package-lock.json` (the harness detects the package manager from the lockfile) |
| Language / build | TypeScript `strict` (plus `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`), React 19, Vite |
| Routing / data | React Router (data routers, URL-driven state for FR-003), TanStack Query for server state and polling of order status (FR-009; polling every 5 s while a payment is `pending`, stopped on a final status) |
| API client | `openapi-typescript` generates types from `specs/004-.../contracts/openapi/*.yaml` and `contracts/openapi/*.yaml` of this feature at build time into `frontend/src/api/generated/` (git-ignored; regenerated by `npm run generate`, verified unchanged in `lint`); `openapi-fetch` as the thin typed client. Hand-written response types are forbidden (constitution VII) |
| Forms / validation | Value-object style validation modules in `frontend/src/domain/` (pure TypeScript, property-tested), React Hook Form for binding; server remains the authority |
| Styling | CSS Modules with design tokens; no CSS-in-JS runtime (CSP-compatible: no inline styles or scripts; `index.html` carries no inline script) |
| Unit tests | Vitest + fast-check (property-based by default for `domain/` and `telemetry/` modules), Testing Library for components (MSW to stub the API at the network edge) |
| Contracts | Pact JS consumer tests, one pact per provider (identity, catalog, cart, order, payment, gateway browser-session and telemetry routes); published to the Pact Broker by the storefront pipeline; providers already verify every consumer in `build/pacts` |
| Acceptance | Cucumber.js + Playwright in `frontend/acceptance/`, behaviour-level Gherkin reusing the ubiquitous language of `acceptance/*.feature`; runs only when `STOREFRONT_URL` is set (same gate as the JVM suite) |
| Accessibility | `@axe-core/playwright` in acceptance (zero critical/serious, SC-006); ESLint `jsx-a11y` |
| Mutation | Stryker (`@stryker-mutator/vitest-runner`) on `domain/`, `telemetry/`, `session/` with a 80 % threshold; the harness already runs Stryker when `frontend/stryker.config.*` exists |
| Lint / format | ESLint (typescript-eslint strict, react-hooks, jsx-a11y, no-restricted-syntax for `dangerouslySetInnerHTML` and `localStorage`), Prettier; `npm run lint` = `prettier --check`, `eslint --max-warnings 0`, `tsc --noEmit`, generated-types freshness |
| Security | CSP for the storefront route (see §6), no `dangerouslySetInnerHTML`, no `localStorage` (lint rule), `sessionStorage` only for the random telemetry session id, dependency scanning via `osv-scanner` on `package-lock.json` in CI (same tool as the services) and `npm audit --audit-level=critical` locally |

**Rationale**: every item is either named by the constitution's Technology Stack or the smallest
standard choice that satisfies a spec requirement; the typed client from OpenAPI is the only way to
meet "API clients MUST be typed from the contract".

**Alternatives**: Next.js or Remix (server runtime, SSR not needed, see §1); Redux (TanStack Query
covers server state, local UI state stays in components); Tailwind (fine, but adds a build step and
class strings that make CSP and a11y review noisier; tokens + CSS Modules keep it minimal);
Zod-generated clients (`openapi-zod-client`) rejected for now: validation at the boundary is done
by the domain modules and the server; types alone are enough.

## 6. Security headers for the storefront route

**Decision**: The gateway keeps its strict defaults for API responses (`default-src 'none'`) and
applies a storefront policy on the catch-all route only:
`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: https:; connect-src 'self'; font-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'`,
plus `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy` denying camera,
microphone, geolocation and payment. `img-src https:` is needed because product images are external
URLs registered by operators (catalog contract). The policy lives in `EdgeHeaders` with a unit test
and is reported to the browser's `report-to` only in a later feature.

**Rationale**: the bundle must run under CSP without `unsafe-inline` (constitution VII); the API
policy would block the page entirely.

**Alternatives**: letting the static container set headers (two places to review; the gateway would
overwrite them anyway).

## 7. Storefront image and Compose integration

**Decision**: `platform/docker/Dockerfile.storefront`: stage 1 `node:24-alpine` (digest-pinned)
runs `npm ci --ignore-scripts` and `npm run build` with `--silent`; stage 2 copies `dist/` into
`nginxinc/nginx-unprivileged:stable-alpine` (digest-pinned) with a minimal `nginx.conf` (SPA
fallback, gzip, cache headers, `/healthz` for the HEALTHCHECK, no server tokens). Compose service
`storefront` (profile `core`, `mem_limit` 64m, network `internal`, healthcheck on `/healthz`); the
gateway gets `STOREFRONT_URL` (default `http://localhost:8082` outside Compose) in
`docs/service-conventions.md`. `.github/workflows/storefront.yml` mirrors the service pipelines:
path-filtered, `npm ci`, `lint`, `test`, Stryker, Pact publish, `osv-scanner`, image build, Trivy,
SBOM, `image-health.sh storefront <image>` (extended to probe `/healthz` on 8080 for this service),
publish on `main`.

**Rationale**: same shape as the seven JVM images, so CI, the registry, the health check script and
the resilience script need no new concepts; the build stage keeps Node out of the runtime image.

**Alternatives**: building the bundle on the host and bind-mounting it (breaks the "one documented
command" start on a fresh machine); Caddy (fine too; nginx-unprivileged is already the common
digest-pinned rootless choice and needs no plugin).

## 8. Bootstrap command: `scripts/dev-env.sh` with subcommands, offline-tested like feature 003

**Decision**: One entry point, `scripts/dev-env.sh` (POSIX-leaning Bash, `set -euo pipefail`,
sourcing `scripts/lib/common.sh` and `platform/compose/scripts/lib.sh`), with subcommands:

| Subcommand | Does |
|------------|------|
| `init` (default) | checks → configure (`.env` from example, generate `IDENTITY_SIGNING_KEY` and `BROWSER_SESSION_KEY` when empty, `git config core.hooksPath .githooks`, `~/.testcontainers.properties` `ryuk.disabled=true` on Podman, `BUILDAH_FORMAT=docker` hint/`.env` line, free `GATEWAY_PORT` detection) → optional `--start` (Compose core + observability `up -d --build`, `wait_healthy`, smoke checks incl. `GET /` returns the storefront, print addresses) |
| `check` | the checks only; exit 0 or 3 |
| `status` | component health table, addresses, engine resources, checks |
| `update` | `up -d --build` for changed components only (Compose build cache), keep data, check |
| `reset` | confirm → `down -v` of platform containers only → `up -d --build` → wait → check |
| `down` | `down` (or `down -v` with `--volumes`), report |

Flags: `--install` (opt-in installs via Homebrew on macOS, `apt`/`dnf` on Linux, SDKMAN for the
JDK; each announced), `--yes` (non-interactive consent for reset/data loss), `--dry-run`,
`--runner-host` (adds the `ci` profile: Pact Broker, and `platform/ci-runner`'s registry compose;
ends by printing the registration procedure link), `--verbose`. Exit codes: 0 ok, 2 usage,
3 prerequisites missing, 4 platform failed to start or failed checks. Checks: JDK (`.java-version`
pin), container engine reachable + Compose v2, engine memory ≥ 10 GiB / CPUs ≥ 4 / free disk
≥ 15 GiB, Podman detection (socket shim, `BUILDAH_FORMAT`, keyring quota note), Node 24 + npm
(`frontend/.nvmrc`), `gitleaks`, `curl`, `jq`, `openssl`, free `GATEWAY_PORT`. Each check prints
`PASS`/`FAIL`/`SKIP (no network)` with found/expected and a remediation per OS. Tests:
`scripts/tests/test_dev_env_*.sh` with stubbed `docker`, `podman`, `java`, `node`, `brew`, `gh`
binaries in `scripts/tests/stubs/`, run by `scripts/tests/run-all.sh`; shellcheck already runs on
`platform/` scripts in the platform workflow and is extended to `scripts/`.

**Rationale**: feature 003 established this exact style (idempotent steps, `run` wrapper for
dry-run, stub-based offline tests); `lib.sh` already has `detect_compose`, `ensure_env`,
`wait_healthy`, `http_status`. A single script with subcommands is discoverable and keeps one
place for the checks the status command reuses (FR-027).

**Alternatives**: a Makefile or `just` (another tool to install, no better testability); Gradle
tasks (needs the JDK before it can tell you the JDK is missing); a Node or Python CLI (adds a
prerequisite to the thing that checks prerequisites).

## 9. Installing prerequisites (opt-in)

**Decision**: `--install` maps each failing check to one package-manager command: macOS Homebrew
(`brew install --cask docker` is *not* run: the engine choice, Docker Desktop vs Podman, is printed
as a decision for the developer; `brew install podman gitleaks jq node@24 openssl` are run);
Linux `apt-get`/`dnf` for `podman podman-compose`/`docker-compose-plugin`, `gitleaks` (from its
release when no package), `jq`, Node via the distro or `fnm`; the JDK via SDKMAN (`sdk env install`
reading `.sdkmanrc`) on both. Every command is printed before running, runs under `run` (dry-run
aware), and `sudo` is invoked only through an explicit `--install` confirmation prompt per command.

**Rationale**: matches FR-021; package managers are the only installers the repository can trust
without downloading arbitrary binaries.

**Alternatives**: curl-pipe-sh installers (forbidden: untrusted downloads); Nix or devcontainers
(good later, but a new paradigm for contributors and not requested).

## 10. Acceptance suite integration

**Decision**: Storefront acceptance scenarios live in `frontend/acceptance/features/*.feature`
(Cucumber.js + Playwright, Chromium only locally and in CI), reusing feature 004's scenario wording
and tags (`@us1`…`@us6`). They run in the platform workflow after the JVM suite when
`STOREFRONT_URL` (= `GATEWAY_URL`) is set, and in `quickstart.md` §5. The JVM suite's
`platform-observability.feature` gains a scenario asserting that a storefront page view appears in
Tempo/Loki with the correlation id (SC-011). The seeded operator and the simulated payment method
tokens from 004 are reused.

**Rationale**: constitution V/VII require behaviour-level acceptance for the frontend; keeping the
features beside the storefront keeps the npm package self-contained while the words stay those of
the business.

**Alternatives**: driving the browser from Cucumber JVM with Playwright Java (splits the frontend's
quality tooling across two ecosystems).

## 11. Versions check (2026-10-04)

Node 24 is the current Active LTS (24.18 installed locally; Node 26 enters LTS later this month and
is not required). React 19, Vite, Vitest, Playwright, Stryker, Pact JS and OpenTelemetry JS web
packages are taken at their latest stable at implementation time and pinned by
`package-lock.json`; `gradle/libs.versions.toml` stays the only place for JVM versions, and the
`checkVersionLiterals` guard already skips `node_modules/`. No constitution amendment is needed.
